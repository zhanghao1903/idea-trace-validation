# LP-05 deployment and recovery runbook

This runbook prepares and operates one synthetic-data Idea Trace Validation deployment. Repository implementation,
code review, merge, server deployment, DNS changes, database restore, and publication are separate authorities. Do
not run an external command until the exact candidate, host, domain, operations, exclusions, and proposal digest
have been presented to the user and explicitly authorized.

## 1. Supported host and hard stop conditions

Production preflight accepts only:

- Linux on `linux/amd64` or `linux/arm64`;
- Docker Engine `>=27.5.0 <30.0.0` from the official Docker package source;
- Docker Compose plugin `>=2.32.0 <3.0.0` (never legacy `docker-compose`);
- age `>=1.2.0 <2.0.0` from an OS package or checksum-verified official release;
- public DNS records resolving only to the authorized public host IPs;
- inbound TCP 80/443, with PostgreSQL and app ports not published;
- separate absolute deploy, backup, and secret roots owned by the operator.

Stop before mutation on `TOOLCHAIN_UNSUPPORTED`, `COMPOSE_CAPABILITY_MISSING`, an unknown install source, a private
or changed DNS/IP, insufficient disk, a symlink/root/repository/Web path, a dirty/mismatched candidate, or missing
authorization. The default local macOS/Docker Desktop environment is useful for typed `LOCAL` evidence only; it is
not production proof.

## 2. Build and transfer an exact candidate

From a clean reviewed feature head, or from the authoritative base commit after squash merge:

```bash
nvm use
npm ci
npm run release:lp05:candidate -- --platform linux/amd64
```

The command runs the complete repository `verify` gate, creates `.lp05-release/<releaseId>/manifest.json` and an
OCI archive, and prints the manifest path. For arm64, use `linux/arm64`. The archive is a local transfer artifact,
not a registry publication.

Before and after transfer, verify the manifest and archive under their exact directory:

```bash
npm run release:lp05:verify-candidate -- \
  --manifest .lp05-release/<releaseId>/manifest.json \
  --reviewed-head <40-character-reviewed-head>
```

For a production candidate after squash merge, also use `--production --merge-commit <merge-sha>
--reachable-from-base`. The production `sourceCommit` is the authoritative merge commit reachable from the
configured base; it is not required to exist in feature-branch history.

Compare the SHA-256 and byte size before loading. Never accept `latest`, a caller-written image ID, a dirty source
tree, a manifest outside `.lp05-release`, or a manifest whose platform differs from the host.

## 3. Host directory and secret preparation

Example layout (replace only with separately authorized absolute paths):

```text
/srv/idea-validation/             deploy root
/srv/idea-validation-backups/     encrypted backup root
/etc/idea-validation/secrets/     three runtime secret files
/etc/idea-validation/age/         backup recipient and restore-only identity
```

Use exact mode `0700` for the runtime-secret directory and exact mode `0644` for
its three Compose source files. The non-root containers require those file read
bits because standalone Compose does not remap file-secret ownership; host
confidentiality comes from the non-traversable `0700` directory and service-scoped
mounts. Keep the separate age decryption identity at `0600`. Follow
[`deploy/secrets/README.md`](../../deploy/secrets/README.md). Generate independent values outside the repository:

```bash
openssl rand -base64 48 > /external/secrets/postgres_password
openssl rand -base64 48 > /external/secrets/ai_api_token
openssl rand -base64 32 | tr '+/' '-_' | tr -d '=' > /external/secrets/human_control_token
age-keygen -o /external/age/backup-identity.txt
age-keygen -y /external/age/backup-identity.txt > /external/age/backup-recipient.txt
```

Do not paste these values into a prompt. Do not place passwords, bearer tokens, cookies, database URLs, the age
identity, TLS data, or raw response bodies in Git, Compose environment files, image layers, command arguments,
screenshots, logs, or evidence. Runtime files are mounted under `/run/secrets`; the app entrypoint rejects symlinks,
empty/oversized files, and equal AI/human values.

Copy `deploy/release.env.example` to an external `release.env` and replace every placeholder with verified
non-secret candidate/target values. Set `SECRETS_ROOT` in the operator shell, not in the tracked example.

## 4. Read-only preflight and deployment authority

Read the host OS, Docker/Compose/age versions and install sources, public DNS/IPs, filesystem identities/free space,
existing Compose labels, existing release marker, existing production volume/database identity, and current image.
Do not create a volume, load an image, start a container, change DNS, request a certificate, or write a record yet.

Create the closed `DeploymentProposalV1` described in
[`evidence-schema.md`](../feature/lp-05-deployment-release/evidence-schema.md). Present the exact canonical JSON and
`proposalSha256`. The user response must bind that digest and the target/candidate/operation set. Requirements,
plan/code approval, merge, or a prior deployment does not substitute for this authorization.

The resulting `DeploymentAuthorizationEnvelopeV1`:

- is immutable, source-task-bound, expires in at most 24 hours, and starts at most one attempt;
- requires all normal deployment/recovery operations and explicitly excludes DNS change, production DB restore,
  tag, GitHub Release, package, registry, and Skill publication unless separately authorized;
- cannot be reused after terminal failure, expiry, or any candidate/target/operation change.

## 5. First install and upgrade order

Render and validate without exposing secret values:

```bash
npm run deploy:lp05:validate
docker compose -f deploy/compose.production.yaml config
docker run --rm \
  -v "$PWD/deploy/Caddyfile:/etc/caddy/Caddyfile:ro" \
  docker.io/library/caddy:2.10.2-alpine@sha256:4c6e91c6ed0e2fa03efd5b44747b625fec79bc9cd06ac5235a779726618e530d \
  caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
```

An authorized attempt follows exactly:

```bash
npm run deploy:lp05 -- --request /external/evidence/deployment-controller-request.json
```

The request contains only the closed host runtime inputs needed to perform the authorized operations; it cannot
provide future phase results or a completed evidence bundle. The controller derives the attempt journal path under
the authorized state root, atomically binds the sanitized runtime, takes a race-safe single-target lock, actively
performs each phase, atomically writes its own closed `ActivePhaseOutputV1`, re-reads the authorization and live
identities, and only then appends the matching transition. If post-phase authority/deadline validation fails, the
controller uses only the already-bound attempt to persist `FAILED -> ROLLING_BACK -> ROLLED_BACK|ROLLBACK_FAILED`;
that safety path cannot authorize another forward phase. The four-hour controller deadline terminates active
backup/restore child pipelines. Caller-authored `PASS`, missing operations, stale runtime identity, or direct
forward re-entry fail closed. The completed bundle is accepted only by the separate offline verifier after the
active attempt finishes. A crashed process may recover a stale lock through an exclusive recovery lease and use one
bounded early `INTERRUPTED -> RESUMING` path only while authority and reconciled outputs remain current. Expired,
drifted, resumed, or post-deploy-backup interruptions are terminalized instead; this also invokes exact isolated
restore cleanup. A live contender, second resume, wrong attempt, or ordinary forward re-entry is rejected.
Fresh attempts set `previousEnvironment` to `null`. Upgrade attempts provide the previously inspected, non-secret
Compose environment projection; its canonical digest must equal `previousRelease.configSha256`. Rollback inspects
the previous image, recreates only `app`/`caddy` from that exact projection, then verifies the exact image,
readiness and core reads. Secret values remain in the unchanged external secret files and never enter the request.

1. load and inspect the exact OCI candidate;
2. re-run read-only preflight and bind `sourceDatabase` when the production DB is actually observed;
3. for an upgrade, create and verify `PRE_MIGRATION_SAFETY`; for a fresh target, prove no prior release, production
   volume, or app data, then start/inspect the new DB before `SAFETY_BACKUP_RESOLVED`;
4. start PostgreSQL and wait healthy; run the one-shot migration and require exit 0;
5. start the exact app image and require `/health/ready = READY`;
6. validate/start Caddy, trusted TLS, an exact same-host HTTP-to-HTTPS redirect, the exact production CSP,
   security/cache headers and boundary semantics;
7. run `EXTERNAL_INITIAL` smoke and the complete LP-04 synthetic journey;
8. create a new `POST_DEPLOY_RECOVERABILITY` backup from that exact database after the story exists;
9. restore that exact ciphertext into the generated `lp05-restore-*` environment, verify all migration checksums and
   equal public synthetic reads, then remove only the exact labelled restore resources;
10. prove production before/after resource identity byte-equality;
11. run `EXTERNAL_POST_RESTORE` against the real domain with equal target/candidate/story/assertion-set identities;
12. only then append `DEPLOYED` and emit `DeploymentEvidenceV1`.

Compose order is PostgreSQL healthy → migration exit 0 → app healthy → Caddy. The separate restore topology is
loopback-only and labels its exact DB container and volume. Compose dependency conditions are not evidence; the
controller actively runs bounded operations, persists its own phase outputs and revalidates authority before every
transition.

Both production identity readers use the validated `POSTGRES_USER` and `POSTGRES_DB` as explicit `psql --username`
and `--dbname` arguments. The container OS user remains `postgres`, but neither `PGUSER`, a default database role,
nor an ambient connection value may select the database principal. A missing or wrong configured role fails before
trusted identity or cleanup authority is established.

Before creating the restore project, the controller persists `restore-lifecycle.json` as `CREATING`; after exact
container/volume/system inspection it becomes `READY`. At the four-hour deadline the controller requests
cancellation from the active oracle and its nested Docker children, then waits for that actor to settle before any
rollback. Cleanup first persists `QUIESCING`; success, any handled restore fault, deadline abort and late stale-lock
recovery inspect the persisted project identity and all matching labels, freeze the complete container/network/volume
identity set, re-inspect each identity immediately before deleting the immutable container/network ID or exact volume
name, and require consecutive empty observations before persisting `CLEANED`. A failed cleanup
persists `CLEANUP_FAILED`, makes rollback fail closed, and never removes production resources or encrypted backup
files. Normal forward restore cleanup first writes the immutable attempt-local
`forward-restore-cleanup.json` authority and binds its digest into the V2 lifecycle. If a later phase fails, rollback
re-resolves that authority, proves the restore project is still empty and does not issue a second delete. If the
process dies after the frozen restore set was fully deleted but before that forward record exists, restart may
recover only from the exact `QUIESCING` V2 record with a nonempty frozen set and fixed consecutive empty project
observations; it derives the removal digest from the frozen authority and never repeats deletion. Partial deletion,
nonempty drift, or the equivalent production state remains fail-closed and requires operator investigation. Before
actual rollback performs application rollback or any new project deletion, it checks the fixed forward record: an absent file follows the
recovery rule above, exact matching content is resolved and reused, and malformed/digest-invalid/wrong-bound content
aborts without new Docker deletion, rollback aggregate or terminal success evidence.

## 6. Health, logs, and routine status

Public checks:

```bash
curl --fail --silent --show-error https://<authorized-domain>/health/live
curl --fail --silent --show-error https://<authorized-domain>/health/ready
curl --fail --silent --show-error https://<authorized-domain>/openapi.json
```

`live` only proves the process responds. `ready` must prove database connectivity and the exact migration ledger.
Inspect bounded, redacted Compose logs; never copy arbitrary logs into evidence:

```bash
docker compose -f deploy/compose.production.yaml ps
docker compose -f deploy/compose.production.yaml logs --since 15m --tail 200 app postgres caddy
npm run ops:lp05 -- --observations /external/evidence/ops-observations.json
```

The status command emits only timestamps, digests, `PASS|FAIL`, and stable reason codes: `APP_UNHEALTHY`,
`DATABASE_UNHEALTHY`, `RESTART_LOOP`, `CERTIFICATE_EXPIRY_RISK`, `DISK_SPACE_LOW`, `BACKUP_STALE`,
`BACKUP_TIMER_FAILED`, and `SMOKE_FAILED`.

## 7. Encrypted backup, retention, and isolated restore

`backup:lp05` accepts a closed non-secret request record. PostgreSQL connection fields, age recipient, and
restore-only identity come from protected runtime configuration. `pg_dump --format=custom` streams directly to age;
plaintext is never written. The command decrypts only through a pipe into `pg_restore --list`, atomically publishes
the ciphertext/manifest pair with restrictive modes, and returns a sanitized manifest.

```bash
npm run backup:lp05 -- --request /external/evidence/backup-request.json
```

The daily systemd examples are under `deploy/systemd/`. Retention keeps the newest seven verified pairs and every
backup referenced by an active/final attempt; a failed new backup never causes deletion. Expired pairs are first
quarantined by exact ID. Never use a glob, `/`, a home directory, repository, Web root, deploy root, or symlink as a
cleanup target.

Restore only the exact `POST_DEPLOY_RECOVERABILITY` pair into a generated loopback-only project/database ending
`_restore`:

```bash
npm run restore:lp05 -- --request /external/evidence/restore-request.json
```

The request must bind the envelope, attempt, target, candidate, ciphertext, complete production resource identity,
migration catalog, and initial story. It declares the isolated DB project/container/volume/name and descriptive
loopback endpoint; the CLI does not accept `PGHOST`, `PGPORT`, `PGDATABASE`, or a password as independent restore
authority. Immediately before mutation it actively re-inspects the production identity and the declared isolated
Compose project/container/volume labels plus live DB system identity. `pg_restore` is then executed with
`docker exec --interactive --user postgres <exact-container-id>` inside that same re-inspected container; no host
socket or caller-selected port can redirect the import. Production and isolated identities must all differ. A
restore failure never triggers production DB restore.

## 8. Credential rotation

Prepare new AI/human values as protected files. Provide an exact previously committed synthetic AI request/body/key
for idempotent replay; it must not create a new write. Set `NEXT_AI_TOKEN_FILE`, `NEXT_HUMAN_TOKEN_FILE`,
`ROTATION_AI_REPLAY_FILE`, `ROTATION_ORIGIN`, and `SECRETS_ROOT`, then run:

```bash
npm run rotate:lp05
```

The app alone restarts. Proof requires old AI rejected, new AI returning an idempotent replay, old human-control
rejected, and new human-control reaching a non-existent confirmation as authenticated `404`. Failure restores both
old files and restarts the prior app. The AI Skill never receives either human-control value or confirmation cookie.

## 9. Failure and rollback

Any oracle failure is terminal for the envelope. Disable public ingress before recovery. For an upgrade, restore the
previous exact app image/config, wait ready, and re-run core public reads. Keep additive migrations and preserve all
production resources. For a fresh install only, automatic resource cleanup is permitted when the attempt persisted
an empty pre-mutation project, every live production/restore resource carries the exact project/environment/role plus
attempt/target/candidate labels, `previousRelease` is null, the configured database principal proves every
application-owned public table empty, and the resource set remains byte-equal through just-in-time inspection.
Cleanup removes only frozen exact IDs/names and proves consecutive zero observations; it never runs project-wide
`compose down`, resets/drops production data, performs a down-migration, or restores a production database.

If any ownership label, lifecycle record, row count, identity, set equality, deletion, or quiescence proof is
missing or changes, recovery records `ROLLBACK_FAILED`, preserves all evidence, and stops for manual inspection. Do
not improvise a broad cleanup command. A repaired and merged implementation requires a newly built candidate and a
new proposal/authorization; a proposal tied to the superseded candidate must remain retired.

Production database restore is a separate destructive operation. It requires demonstrated old-app incompatibility,
an exact verified safety backup, a new proposal listing `PRODUCTION_DB_RESTORE`, and new explicit user authorization.

The idempotent manual recovery entrypoint operates only on the exact persisted `FAILED`/`ROLLING_BACK` attempt:

```bash
npm run deploy:lp05:rollback -- --request /external/evidence/rollback-request.json
```

External smoke never consumes caller-authored assertions. Use the exact envelope/attempt request form; the origin is
derived from the authorized target and DNS, TLS, ports, HTTP boundaries, runtime identity/logs/health and the LP-04
journey are actively observed:

```bash
npm run deploy:lp05:smoke -- --request /external/evidence/external-smoke-request.json
```

`--observations` remains available only for typed `LOCAL` fixtures and fails for either external mode.

## 10. Evidence, acceptance, and publication boundary

Validate an exact bundle with:

```bash
npm run deploy:lp05:verify-evidence -- --bundle /external/evidence/deployment-bundle.json
```

This is an offline, post-attempt verifier. Its bundle is never an input to `deploy:lp05` and cannot advance the
attempt journal or replace any active host operation.

Keep immutable canonical records and encrypted backups through feature closure. Local/fixture evidence is permanently
typed and cannot satisfy external states. `DEPLOYED` is operational evidence, not Engineering Lifecycle acceptance.
After merge and successful real external evidence, present the merge SHA and final evidence digest to the user for
separate `acceptance-only/no-publish` authorization. Default scope publishes no tag, GitHub Release, package,
registry image, or marketplace asset.
