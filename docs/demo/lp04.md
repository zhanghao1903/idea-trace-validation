# LP-04 本地演示指南

本指南只针对仓库自带的合成场景和操作者拥有的本地隔离环境。业务写入始终经过现有
HTTP API；`.lp04-demo/` 只保存可恢复请求日志和脱敏证据，不是第二份业务状态。

## 1. 前置条件与安全检查

- 使用仓库要求的 Node.js、npm、Docker 和本地 PostgreSQL。
- 目标必须是 `http://127.0.0.1`、`http://localhost` 或 `http://[::1]`；工具会拒绝
  HTTPS、用户信息、路径、查询参数和非回环主机。
- 数据库必须是操作者拥有、名称以 `_test` 结尾的隔离库。不要对共享、开发或生产数据库
  运行清理命令。
- AI bearer 只从进程环境注入。不要把真实值写入命令参数、Skill、演示 manifest、日志、
  截图或证据。
- `HUMAN_CONTROL_TOKEN` 是独立的人类能力材料，绝不能提供给 Codex、Claude 或 demo
  runner。

启动仓库自带的隔离数据库并构建应用：

```bash
npm run test:db:up
npm run build
```

在一个终端中使用占位符所代表的安全本地配置启动 API。不要把下面的占位符替换结果
提交到 Git：

```bash
export NODE_ENV=test
export DATABASE_URL="$TEST_DATABASE_URL"
read -s AI_API_TOKEN
export AI_API_TOKEN
read -s HUMAN_CONTROL_TOKEN
export HUMAN_CONTROL_TOKEN
export WEB_DIST_DIR="apps/web/dist"
npm run dev
```

确认 `GET /health/ready` 返回 `ready` 后再继续。`<skill-commit>` 必须是包含当前
`skills/idea-validation-workflow/` 且可由 Git 解析的完整 40 字符提交 SHA。

## 2. 自动化真实 HTTP 故事

在第二个终端只注入相同 AI bearer，然后运行：

```bash
read -s AI_API_TOKEN
export AI_API_TOKEN
npm run skill:check
npm run demo:lp04 -- \
  --base-url http://127.0.0.1:3000 \
  --run-id lp04-manual \
  --skill-commit <skill-commit>
npm run demo:lp04:verify -- \
  --base-url http://127.0.0.1:3000 \
  --run-id lp04-manual \
  --skill-commit <skill-commit>
```

第一次执行创建带 `SYNTHETIC_DEMO_DATA` 标记的 Idea、项目、执行事实和结构化汇报。
再次使用完全相同的 run ID、Skill commit 和 manifest 执行时，只做幂等重放与公开重读，
不会创建第二份权威对象。不同 run ID 会创建另一组明确标记的合成故事。

预期验证结果为 `result: PASS`，并包含非零 request/resource 数量。任何未解决 journal、
Skill/manifest 绑定变化、正文或版本漂移、资源无法公开重读都会 fail closed。

## 3. Codex 与 Claude 加载

- Codex：在仓库中调用 `$idea-validation-workflow`，并确认它加载
  `skills/idea-validation-workflow/SKILL.md` 及链接的 references。
- Claude：通过客户端支持的本地 Skill 入口加载同一目录，不复制或改写 `SKILL.md`。

给客户端的输入只包含合成自然语言意图和回环 API 地址。AI bearer 必须由客户端安全配置
或进程环境注入，不能出现在提示词。客户端应先读 OpenAPI/current authority，再冻结 method、
path、canonical body 和 `Idempotency-Key`；网络结果未知时只能原样重放。客户端遇到
human confirmation 时解释公开人工步骤并停止。

只有实际客户端调用了真实 API、留下请求 ID、资源可公开重读，并让验证器同时读取已提交
证据和本地忽略的原始 transcript 时，才可生成对应客户端的 PASS 记录：

```bash
npm run demo:lp04:verify-client -- \
  --base-url http://127.0.0.1:3000 \
  --file docs/feature/lp-04-ai-skill-demo/evidence/<client>-client-proof.json \
  --transcript <ignored-raw-client-transcript.jsonl>
```

验证器会重算 transcript 摘要并验证闭合的 POST request claims：成功请求必须同时匹配资源
的公开审计事件及其固定 method、exact path、status 语义；客户端可解析时还要匹配 tool
request/result。没有审计事件的拒绝请求必须从客户端 tool request/result 精确配对 method、
path、status 和 response request ID。每个 objective PASS 由恢复事实、审计与公开读回重新
推导。静态回答、mock、同资源错操作/错状态、任意 PASS 标签、无关资源或缺少认证会话都
不能替代。

## 4. 双角色 Web 验收

真实数据 Chromium 故事会独立构建、清理确切的 `_test` 数据库、经 HTTP 生成场景，并验证
proposer/executor 读取同一项目 ID：

```bash
npm run test:browser:lp04
```

预期可见内容包括 Idea 池、执行中项目、三类关注项、证据优先汇报、独立人工确认上下文、
完成项目和时间线优先汇报。页面不得显示 bearer、human-control 值或写入/确认控件。

## 5. 独立人工交接

自动 demo 只创建需要人类治理的上下文，不使用人类凭据。操作者确认这是合成、本地、隔离
场景后，另行执行：

```bash
read -s HUMAN_CONTROL_TOKEN
export HUMAN_CONTROL_TOKEN
npm run demo:lp04:human -- \
  --base-url http://127.0.0.1:3000 \
  --run-id lp04-manual \
  --allow-human-control-for-synthetic-demo
```

缺少显式 opt-in、manifest 不匹配、token 格式错误或项目不满足确认条件都会停止。命令不打印、
不持久化 token/cookie；完成后公开项目必须显示 `COMPLETED`。

## 6. 失败恢复

- 连接失败且上游未处理：保留 `PREPARED`/`DISPATCHED` journal，以相同 run ID 重启。
- 结果未知：不要修改正文、key、manifest 或 Skill；重启会从 journal 原字节重放并公开重读。
- 422/409：按稳定错误修正意图；变化后的意图使用新的 deterministic key。
- journal 损坏、终态 intent 漂移或资源重读不一致：停止，不删除证据来制造成功。
- 人类拒绝或 capability 缺失：报告公开状态并停止，AI 不代替人类重试。

## 7. 精确清理

确认验证结束后，可以删除**一个确切 run ID** 的本地忽略证据，例如
`.lp04-demo/runs/lp04-manual`；这不会删除 API 业务记录。不要使用 glob、环境变量或仓库根目录
作为删除目标。

只有在该 compose 项目及其 volume 确实由当前操作者为本次测试启动时，才运行：

```bash
npm run test:db:down
```

该命令只停止仓库 compose 项目并删除其命名 volume。共享或生产环境没有自动清理路径。
