## Source Request

先为“CEO 创新想法与快速原型验证系统”形成项目计划书，不立即开始大规模编码。项目需要在 2026-08-06 前形成可部署、可演示的 v0.1，并先明确核心用户旅程、最小领域模型、任务生命周期、各交互面的职责和关键产品决策。

服务对外提供 API 和 Skill。想法提出者或执行者通过 Codex、Claude 等 AI 客户端向站点提交想法或项目更新，站点接受、保存并呈现在网页上。v0.1 只支持“想法提出者”和“执行者”两种视角；网页允许直接切换视角，不建设用户、登录或权限系统。

想法提出者需要知道自己有哪些想法、哪些仍只是暂不验证的 Idea、哪些已经进入执行以及执行进度。执行者需要区分和管理未完成、已完成项目，并汇报进度、待确认问题、难点以及希望获得的支持。项目汇报页面不应硬编码成所有项目相同的固定结构；AI 可以输出经过约束和校验的结构化展示数据，由前端自适应渲染不同项目的汇报内容。

## 项目摘要

本项目面向“帮助 CEO 快速验证创新想法”的工作场景，建设一个由 AI 直接操作、由人最终治理的权威状态系统。它把 Codex、Claude 等 AI 客户端中的想法、澄清、验证进度、困难、支持请求、决策和结论，通过 Skill 和 API 转化为可追踪记录，并通过双角色网页视图呈现。

v0.1 的首要价值不是覆盖完整的项目管理，而是证明一条可信的端到端链路：想法提出者通过 AI 提交内容，站点形成权威记录；执行者通过 AI 汇报进展和问题；双方在无需登录的演示环境中切换对应视角，看到与角色相关的信息；不同项目的汇报结构可随内容变化，但仍保持安全、可理解和可纠偏。

## Problem And Desired Outcome

### 当前问题

- CEO 的创新想法和执行过程主要依赖飞书、企业微信等聊天载体，关键信息容易分散、过期或失去上下文。
- AI 可以快速理解和执行任务，但缺少可供其稳定读写的权威状态和清晰操作边界。
- CEO 与执行者难以快速回答“目前处于什么阶段、遇到什么困难、做过哪些决定、是否值得继续”等关键问题。
- 仅靠人工维护复杂表单会增加负担，无法发挥 AI 作为直接操作者的优势。

### 期望结果

到 v0.1 完成时，用户可以演示一条完整的创新想法验证旅程：想法通过 Codex 或 Claude 被站点接收，停留在 Idea 池或转为执行项目；执行者持续汇报进展、待确认问题、难点和支持请求；AI 为不同项目生成结构化汇报内容，网页按角色和项目自适应呈现；最终沉淀带证据的验证结论。

## Actors

- **想法提出者**：通过 Codex、Claude 等提交或补充想法，决定 Idea 是否进入执行，查看执行进度，回应待确认问题并消费验证结论。
- **执行者**：负责推进原型或 MVP 验证，管理未完成和已完成项目，汇报进展、待确认问题、难点、支持请求、证据和建议。
- **AI 操作者（Codex、Claude 等）**：根据 Skill 理解自然语言意图，通过 API 向站点提交和读取结构化数据，并为网页生成项目相关的结构化汇报内容。
- **系统维护者**：部署 v0.1、配置必要访问方式，并保障演示环境可用。

## Goals

- 建立从想法登记到验证结论的最小闭环。
- 让系统而非聊天记录成为项目状态、问题、决策和结论的权威来源。
- 为 AI 提供清晰、稳定、可验证的操作入口。
- 为想法提出者和执行者提供职责不同、可直接切换的网页视图。
- 让想法提出者清楚区分 Idea 池、等待执行、执行中和已完成内容。
- 让执行者清楚管理未完成和已完成项目，并结构化汇报进度、问题、难点与支持请求。
- 允许不同项目拥有不同的汇报结构，而不要求前端为每种项目单独硬编码页面。
- 在 2026-08-06 前完成可部署、可实际演示的 v0.1。
- 在进入大规模编码前确认核心用户旅程、产品边界和关键决策。

## Non-goals

- 不在 v0.1 中建设通用型或全功能项目管理平台。
- 不替代 Jira、飞书、企业微信等协作工具的全部能力。
- 不要求用户通过复杂表单手工维护全部项目状态。
- 不在 v0.1 中建设注册、登录、账户、成员邀请或权限控制系统。
- 不要求想法一经登记就必须进入验证；Idea 可以长期停留在暂不验证状态。
- 不允许 AI 输出并执行任意前端代码；动态页面只消费系统支持且通过校验的声明式结构化数据。
- 不在本需求快照中确定数据库、框架、云服务或部署拓扑等技术方案。
- 不把 MCP Server 纳入 v0.1 必交范围；本期对外能力为 API 和 Skill。
- 不在 v0.1 中承诺企业级多租户、复杂权限、审计合规、高可用或大规模性能。
- 不在本需求阶段编写逐日实施排期；技术设计与实施计划由 Main Work 在需求确认后产出。

## 核心演示故事

1. 想法提出者在 Codex 或 Claude 中用自然语言描述一个想法，AI 根据 Skill 调用站点 API。
2. 站点接收并保存想法；想法提出者在网页中看到它，并可让它停留在 Idea 池而不进入验证。
3. 当想法提出者决定推进时，Idea 进入等待执行或执行中状态，并与验证项目关联。
4. 执行者切换到执行者视图，看到未完成项目、优先关注项、待确认问题、难点和支持请求。
5. 执行者通过 AI 汇报进展；AI 提交事实数据和项目相关的结构化汇报数据，站点校验后保存。
6. 想法提出者切回自己的视图，看到哪些想法已执行、当前进度、需要自己确认或支持的事项。
7. 不同项目的详情页按各自结构化汇报数据展示不同章节、指标、清单、证据或时间线。
8. 验证结束后，执行者提交结论，想法提出者确认建议去向；项目进入已完成视图并保留历史。

## User Scenarios

### Scenario 1: 登记并澄清创新想法

- Actor: 想法提出者、AI 操作者
- Starting context: 想法提出者在 Codex 或 Claude 中只有一段不完整的自然语言想法
- Action: AI 根据 Skill 提取目标、受益者、待验证假设和缺失信息，通过 API 向站点创建想法记录
- Expected outcome: 站点接受请求并形成唯一、可追踪的权威记录；已知信息与待澄清项清楚分离
- Failure recovery: 信息不足时保留草稿和缺失项，不伪造答案；用户可补充或纠正

### Scenario 2: 管理 Idea 池与执行去向

- Actor: 想法提出者
- Starting context: 站点中已有多个处于不同阶段的想法
- Action: 想法提出者打开自己的视图，查看全部想法，并决定将某个 Idea 暂时保留、继续澄清或进入执行
- Expected outcome: 用户能清楚识别哪些只是 Idea、哪些等待执行、哪些正在执行、哪些已完成，以及每个执行项目的最新进度
- Failure recovery: 错误进入执行的 Idea 可以被暂停或纠正，且原决定保留在历史中

### Scenario 3: 执行者管理项目并汇报进度

- Actor: 执行者、AI 操作者
- Starting context: 执行者负责多个未完成和已完成项目
- Action: 执行者在执行者视图中选择项目，并通过 AI 汇报已完成工作、当前状态、下一步、证据与风险
- Expected outcome: 未完成和已完成项目分组清晰；项目显示最新进度、更新时间和可解释的变化历史
- Failure recovery: 更新失败时不得显示为已成功；操作者能够安全重试并避免重复记录

### Scenario 4: 汇报待确认问题、难点和支持请求

- Actor: 执行者、想法提出者、AI 操作者
- Starting context: 执行过程中出现无法自行决定的问题、难点或资源依赖
- Action: 执行者通过 AI 提交事项的背景、影响、可选方案或建议，以及希望获得的具体支持
- Expected outcome: 事项在双方对应视图中醒目可见；想法提出者能够回应，执行者能跟踪处理状态
- Failure recovery: 信息不足时事项保持待补充；已失效事项可以关闭，但记录和回应历史仍可追溯

### Scenario 5: 沉淀验证结论

- Actor: 想法提出者、执行者、AI 操作者
- Starting context: 验证动作已产生足够证据，或项目需要提前停止
- Action: AI 汇总假设、证据、限制和建议，由人确认结论
- Expected outcome: 项目形成可追溯的结论，并明确建议继续、调整、停止或移交
- Failure recovery: 证据不足时明确标记不确定性，不把推测呈现为已验证事实

### Scenario 6: 切换角色视图

- Actor: 想法提出者、执行者
- Starting context: 系统中已有一个或多个想法和验证项目
- Action: 用户无需登录即可在“想法提出者”和“执行者”视图之间直接切换
- Expected outcome: 两个视图使用同一权威数据，但按角色分别突出想法组合与执行工作台
- Failure recovery: 用户发现错误时可以发起纠正、撤销或重新确认，而不直接破坏历史记录

### Scenario 7: 自适应渲染项目汇报

- Actor: AI 操作者、想法提出者、执行者
- Starting context: 不同项目需要展示不同的章节、指标、列表、证据或说明
- Action: AI 提交声明式结构化汇报数据，站点校验并由网页渲染
- Expected outcome: 项目页面能够随结构化内容变化，不依赖为每类项目单独开发固定页面
- Failure recovery: 数据结构无效或包含不支持内容时，系统拒绝写入或降级为安全的错误提示，上一份有效汇报仍可查看

## 产品职责边界

| 交互面 | v0.1 职责 | 不承担的职责 |
| --- | --- | --- |
| Skill | 指导 Codex、Claude 等 AI 理解两类角色的意图、收集最小必要信息、生成允许的结构化数据、调用 API 并解释结果 | 不自行保存独立项目状态，不绕过 API 校验 |
| API | 接受 AI 客户端请求，提供权威业务操作、生命周期校验、结构化汇报校验、读取能力和可观察错误 | 不负责自然语言理解，不执行 AI 生成的前端代码 |
| Web | 提供可直接切换的想法提出者视图与执行者视图，并渲染经过校验的项目结构化汇报 | 不建设用户系统，不把所有项目硬编码成相同汇报模板 |
| MCP | v0.1 不交付 | 不形成第二套业务模型或独立状态 |

## Constraints

- v0.1 的目标完成日期为 2026-08-06。
- 必须提供可实际演示的端到端版本。
- 必须部署到个人域名和服务器。
- 必须提供 Skill 和结构清晰的 API。
- v0.1 只提供想法提出者和执行者两种可直接切换的网页视图，不建设用户系统。
- API 和 Skill 必须围绕同一权威状态工作；MCP 不属于 v0.1 必交范围。
- 项目汇报页面必须支持 AI 结构化数据驱动的自适应呈现，不能依赖项目专用的固定页面。
- AI 只能提交声明式结构化数据，不能向网页注入或执行任意代码。
- 具体技术方案和逐日排期须在需求确认后由 Main Work 形成。

## Failure And Recovery

- 自然语言输入不完整时，系统保存草稿与缺失项，不虚构信息。
- 业务操作失败时，AI 和人都能辨别失败，不把未落库操作呈现为成功。
- 重试不得无意创建重复想法、项目、进展、决策或结论。
- 状态变化不合法时，系统拒绝变更并解释允许的恢复路径。
- 人类确认与 AI 意图冲突时，以明确的人类决定为准，并保留冲突与修正记录。
- 结论证据不足时，系统明确标记不确定性并允许继续补充验证。
- 结构化汇报校验失败时不替换上一份有效内容，并向 AI 返回可修正的错误位置和原因。
- 结构化汇报渲染失败时显示安全的降级提示，不执行未知内容，也不影响项目权威状态。
- 部署环境不可用时，项目仍应保留可恢复的数据与明确的故障状态；具体备份与恢复指标在技术设计阶段确定。
