## Problem

当前仓库已经确认 v0.1 的产品范围、领域模型、技术架构和五阶段实施计划，但尚没有可运行的应用、持久化数据、API 或锁定依赖。创新想法仍只能停留在聊天和文档中，系统无法形成唯一、可重试、可追踪的权威 Idea 记录，也无法可靠区分“只是一个想法”和“已明确进入执行的项目”。

LP-01 需要建立第一个可运行、可验证的业务切片：Idea 可以被创建和澄清，在没有明确推进意图时持续留在 Idea 池；收到合法的明确推进后，才生成唯一关联项目。该切片必须为后续执行、汇报、Web、Skill 和部署计划提供可信基础，但不能提前吞并后续计划的范围。

## Desired scenarios

1. AI 操作者提交一个完整 Idea，系统创建唯一记录，并返回可再次读取的稳定标识。
2. AI 操作者提交一个不完整 Idea，系统分别保存已知信息、假设和待澄清问题，不虚构缺失内容。
3. 用户补充澄清信息后，系统保留原问题与回答历史，并重新计算 Idea 是否仍需澄清。
4. Idea 没有收到明确推进意图时，即使信息完整也持续留在 Idea 池，不自动创建项目。
5. 想法提出者明确推进一个满足最低条件的 Idea 后，系统创建唯一关联项目并进入等待执行状态。
6. 相同请求因网络未知结果被安全重试时，系统返回原结果而不创建重复 Idea、回答或项目。
7. 冲突载荷、过期版本或非法状态变化被拒绝，调用方能知道错误原因、当前版本和可采取的恢复动作。
8. 想法提出者和执行者的基础读取结果来自同一权威数据，只突出不同字段，不形成两份状态。
9. 成功的创建、澄清和推进操作形成可理解历史，能够说明何时、由哪个声明角色、因何发生变化。

## Goals

- 建立可从干净环境复现的最小应用、共享契约、持久化和验证基础。
- 建立单工作空间内唯一、可追踪的 Idea 权威记录。
- 清楚分离已知事实、假设和待澄清问题。
- 证明“信息完整”不等于“自动进入执行”，推进必须来自明确的人类意图。
- 为每个 Idea 最多创建一个首要验证项目。
- 对 LP-01 写操作提供幂等、乐观并发、事务和追加式历史保证。
- 提供创建、澄清、推进和基础读取所需的版本化 API 与机器可读契约。
- 建立公开读取、AI 写入和必要控制能力的最小访问边界，同时不声称存在用户身份系统。
- 为 LP-02–LP-05 提供稳定基础，不提前实现其业务能力。

## Functional requirements

| ID | Requirement |
| --- | --- |
| LP1-REQ-001 | 项目必须提供一组有文档说明的标准命令，使维护者可从干净检出安装依赖、执行格式/静态检查、运行 LP-01 测试并构建应用。 |
| LP1-REQ-002 | 系统必须在一个预置工作空间中持久化 Idea、澄清、关联项目、幂等记录和操作历史；成功响应前业务事实与历史必须原子保存。 |
| LP1-REQ-003 | 创建 Idea 时必须保存稳定 ID、原始意图摘要、声明的提出者、期望结果、服务端创建时间和当前版本。 |
| LP1-REQ-004 | 系统必须把已知陈述、待验证假设和待澄清问题分别保存；缺失信息不得被补写为事实。 |
| LP1-REQ-005 | Idea 必须具有可解释的 intake 状态，至少区分普通 Idea 与待澄清；信息补充后可以离开待澄清，但不得因此自动进入执行。 |
| LP1-REQ-006 | 澄清回答必须引用对应问题、保留原问题和回答历史，并以追加或可追踪纠正方式更新当前 Idea。 |
| LP1-REQ-007 | 推进 Idea 必须是独立、显式操作，并至少要求可验证目标、一项待验证假设和想法提出者的明确推进意图。 |
| LP1-REQ-008 | 每个 Idea 在 v0.1 最多关联一个首要验证项目；重复推进不得创建第二个项目。 |
| LP1-REQ-009 | 合法推进后创建的项目必须包含稳定 ID、来源 Idea、目标、假设、当前阶段、等待执行状态、版本和服务端时间，并可被基础查询读取。 |
| LP1-REQ-010 | LP-01 必须执行 Idea 创建、澄清和推进所需的最小生命周期规则；不允许的重复推进、缺条件推进或与当前状态冲突的操作必须被拒绝。 |
| LP1-REQ-011 | 所有 LP-01 写请求必须携带调用方生成的幂等标识；相同标识与相同意图重试返回原成功结果，不新增业务记录。 |
| LP1-REQ-012 | 相同幂等标识携带不同意图时必须返回明确冲突，不得采用任一新载荷或覆盖原结果。 |
| LP1-REQ-013 | 更新已有 Idea 或项目的操作必须检查预期版本；过期版本不得覆盖更新后的事实，并返回当前版本或重新读取提示。 |
| LP1-REQ-014 | 每个成功业务写入必须留下同事务的历史记录，至少包含操作类型、对象、版本、服务端时间、声明的操作者、原因和请求关联标识。 |
| LP1-REQ-015 | API 必须返回一致的结构化成功与错误结果；错误至少包含稳定错误码、人可理解说明、是否可重试，以及适用时的字段位置、当前状态或恢复提示。 |
| LP1-REQ-016 | API 必须覆盖 Idea 创建、澄清回答、显式推进、Idea 列表/详情和基础项目列表/详情，并提供机器可读的版本化 API 契约。 |
| LP1-REQ-017 | 想法提出者与执行者的基础查询必须读取同一权威数据；视图参数只能改变投影重点，不得创建或修改独立状态。 |
| LP1-REQ-018 | AI 写入必须受部署凭据保护；公开读取与必要控制能力必须有清晰边界。Actor/role 字段只表示声明归属，不得描述为已认证用户身份。 |
| LP1-REQ-019 | 日志、错误、历史和 API 契约不得包含访问 token、cookie、数据库连接秘密或完整敏感请求正文。 |
| LP1-REQ-020 | 现有结构化汇报 Schema 必须作为后续计划可复用的共享契约保留并通过基础契约检查；LP-01 不提供汇报提交 API 或渲染能力。 |
| LP1-REQ-021 | LP-01 的领域、契约、持久化和 API 行为必须有自动化测试，至少覆盖成功、信息不完整、非法推进、幂等重放、幂等冲突、版本冲突和事务失败。 |
| LP1-REQ-022 | 项目必须提供可观察的存活与就绪状态；持久化或迁移未就绪时不得报告可处理业务请求。 |

| LP1-AC-002 | LP1-REQ-003–005 | Given 输入缺少目标或假设，when 创建 Idea，then 系统创建唯一记录并分别保存已知信息、假设和待澄清问题，状态为待澄清且没有项目。 |
| LP1-AC-003 | LP1-REQ-005–006 | Given 一个待澄清 Idea，when 回答问题，then 原问题与回答仍可追溯，当前 Idea 反映补充信息，但在没有推进命令时仍无项目。 |
| LP1-AC-004 | LP1-REQ-007–010 | Given 一个满足最低条件的 Idea，when 想法提出者明确推进，then 系统只创建一个等待执行项目；再次推进返回原关联或确定性拒绝，不创建第二个项目。 |
| LP1-AC-005 | LP1-REQ-007、LP1-REQ-010、LP1-REQ-015 | Given Idea 缺少目标、假设或明确推进意图，when 请求推进，then 系统拒绝且返回可定位原因和恢复提示，Idea 当前事实不变。 |
| LP1-AC-006 | LP1-REQ-011–012 | Given 同一创建或推进请求，when 以相同幂等标识和相同载荷重放，then 返回首次结果且记录数量不变；更换载荷后返回幂等冲突。 |
| LP1-AC-007 | LP1-REQ-013 | Given 两个调用方基于同一旧版本更新 Idea，when 较晚请求提交，then 系统拒绝覆盖并提供重新读取所需信息。 |
| LP1-AC-008 | LP1-REQ-002、LP1-REQ-014、LP1-REQ-021 | Given 任一成功或模拟事务失败的写入，when 查看业务事实与历史，then 成功时二者同时存在，失败时二者均未部分保存。 |
| LP1-AC-009 | LP1-REQ-016–017 | Given 系统存在普通 Idea、待澄清 Idea 和等待执行项目，when 分别读取想法提出者与执行者基础投影，then 两者引用相同对象、状态和版本，但展示各自相关字段。 |
| LP1-AC-010 | LP1-REQ-015–016 | Given API 请求成功、输入错误、冲突或服务暂不可用，when 调用任一 LP-01 操作，then 响应遵循机器可读契约并提供稳定错误语义。 |
| LP1-AC-011 | LP1-REQ-018–019 | Given 未携带 AI 写入凭据或使用无效凭据，when 尝试写入，then 请求被拒绝且日志/错误不泄露秘密；公开读取仍遵守既定只读边界。 |
| LP1-AC-012 | LP1-REQ-020 | Given 现有结构化汇报 Schema，when 运行共享契约检查，then Schema 可被后续模块引用且没有出现第二份不受检验的规范源；不存在汇报写入或渲染实现。 |
| LP1-AC-013 | LP1-REQ-022 | Given 数据库不可达、迁移未完成或应用正常，when 查询健康状态，then 就绪结果准确区分不可处理与可处理业务请求。 |
| LP1-AC-014 | LP1-REQ-002–022 | Given LP-01 准备验收，when 执行客观主场景：同一不完整 Idea 请求重放两次、补充澄清、保持不推进、随后明确推进并尝试非法重复推进，then 只存在一个 Idea 和一个项目，全部状态、版本、错误和历史符合本快照。 |

## Non-goals

- 不实现 LP-02 的进展、阻塞、待确认问题、支持请求、证据、结论或高影响确认流程。
- 不实现 LP-03 的结构化汇报提交/版本、通用渲染器、完整想法提出者 Web 或执行者 Web。
- 不实现 LP-04 的 AI Skill、演示数据或完整端到端演示脚本。
- 不实现 LP-05 的生产部署、域名、HTTPS、备份恢复或发布候选验证。
- 不建设注册、登录、账户、成员邀请、权限组、多租户或企业身份系统。
- 不提供 MCP、通用文件上传、对象存储、WebSocket、消息队列或微服务。
- 不允许 Idea 在 v0.1 关联多个首要验证项目。
- 不在 Requirements 快照中决定包的精确补丁版本、目录结构、数据库表结构或部署拓扑；这些属于 Main 技术计划。
- 不复用 lightweight planning feature 的实现授权；LP-01 必须以本需求快照单独确认和交接。
- 不为本 feature 建立自研 authorization engine、lifecycle simulator、GitHub authority checker 或大规模 mutation harness。

## Failure and recovery expectations

- 输入缺失或格式错误时，不创建部分 Idea；若业务允许保留不完整 Idea，则明确保存待澄清状态和缺失项。
- 客户端在响应未知时使用同一幂等标识重试；系统不得要求调用方猜测第一次是否成功。
- 幂等冲突时保留首次结果，不接受新载荷；调用方必须读取原结果或使用新的标识表达新意图。
- 版本冲突时不自动覆盖；调用方重新读取、合并意图后再提交。
- 非法状态或不满足推进条件时保持当前状态，并返回允许的恢复动作。
- 数据库、事务、迁移或历史写入失败时不得报告成功，也不得留下只写了一半的事实。
- 历史内容错误时使用可追踪纠正，不物理删除或静默改写既有成功操作。
- 持久化不可用时就绪检查失败，恢复后可继续读取已提交数据。

## Public API and compatibility impact

LP-01 将建立项目的首个运行时 API，因此没有既有运行时客户端需要向后兼容。API 必须版本化，并为 Idea 创建、澄清、推进、读取、健康状态以及统一成功/错误结果提供稳定机器可读契约。

后续 LP-02–LP-04 将复用这些 ID、版本、Actor、错误、幂等和读取约定。LP-01 验收后，如需破坏这些公共约定，必须显式修订需求并提供迁移说明，不能静默更改。

## Safety, privacy, permissions, and authorization

- AI 写操作需要部署级凭据；凭据只证明调用来源获准写入，不证明 `actor` 字段中的自然人身份。
- 公开读取意味着演示环境不得放入真实机密 Idea 或个人数据；测试和示例只能使用虚构数据。
- 服务端时间、ID、版本和历史由系统生成，客户端不得伪造为权威字段。
- 所有输入都必须经过大小、结构和业务边界校验；错误不得回显秘密或无关数据。
- 日志只保留诊断所需摘要和关联标识，不保存 token、cookie、数据库连接串或完整敏感正文。
- 本快照不授权生产部署、真实凭据配置、发布或外部数据导入。

## Release impact

- LP-01 是 v0.1 的首个可运行基础切片，不等同于可演示或可发布的完整 v0.1。
- 验收后应把 LP-01 的计划状态和证据更新为相应结果，LP-02 才能按依赖进入验收路径。
- LP-01 不要求生产域名或服务器部署；发布与恢复证明属于 LP-05。

## Assumptions

- v0.1 是无用户系统的单工作空间演示，想法提出者和执行者是声明角色。
- 每个 Idea 最多对应一个首要验证项目。
- 原始产品需求、领域模型、技术架构和 LP-01 计划继续作为设计输入；若与本快照冲突，以本次确认后的 LP-01 需求边界为准。
- Main 将在技术计划中核验并锁定当前兼容依赖版本；当前仓库没有可继承的依赖锁文件。
- 测试可使用隔离数据库或等价持久化环境，不依赖生产服务器。
- LP-01 的基础项目读取是为后续计划提供权威数据，不要求本期交付完整用户界面。
