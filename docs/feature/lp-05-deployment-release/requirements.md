## Problem

LP-01 至 LP-04 已经形成并验收了可运行的 v0.1 业务闭环、双角色 Web、AI Skill 和可重复
演示，但这些能力目前只具备本地运行与测试证据。仓库还没有可用于个人服务器的生产部署
资产、HTTPS 入口、受控迁移流程、备份与恢复工具、部署 smoke 或完整运维文档，因此无法
证明 REQ-026 所要求的“用户可访问的个人域名和服务器”交付。

LP-05 需要把已验收的软件打包为一个可识别版本、可安全启动、可备份恢复、可回滚且可重复
验证的单服务器发布候选，并在用户提供目标和单独发布授权后完成真实 HTTPS 部署。该阶段
只负责把既有 v0.1 可靠地运行起来，不新增产品能力，也不把需求确认本身解释为操作服务器、
DNS 或外部发布的授权。

## Desired scenarios

1. 运维者获得一台符合文档前置条件的空服务器和一个已指向该服务器的个人域名，从一个精确
   版本按文档配置仓库外秘密、执行迁移并启动服务；数据库先健康、迁移成功、应用 readiness
   通过后，公网流量才进入应用。
2. 用户通过个人域名访问 HTTP 时被安全转到 HTTPS；有效证书下的 proposer、executor、
   项目详情、确认页面、API、OpenAPI 和健康检查按各自既有契约工作。
3. 运维者在不查看源码的情况下执行部署 smoke，确认版本、HTTPS、安全响应头、请求大小
   边界、liveness、readiness、数据库连通性和关键只读路径，并得到明确的通过或失败结果。
4. 发布候选只装载 LP-04 的合成演示数据；用户在真实域名上按演示脚本展示 Idea 池、执行中
   项目、进展、问题、支持、两类不同汇报、双视图和完成归档，不暴露真实公司数据。
5. 运维者为当前生产数据库创建受保护备份，将该备份恢复到隔离数据库，验证迁移完整性并从
   恢复数据完成核心演示读取；恢复验证不会覆盖或连接生产数据库。
6. 新版本迁移、启动、readiness 或 smoke 失败时，部署停止在可理解状态；运维者可回到上一
   个已知可用应用版本，数据库和备份保持可追踪，不执行自动 down 或破坏性清空。
7. 运维者轮换 AI 和 human-control 凭据后，旧凭据失效、新凭据工作，日志、命令输出、文档、
   镜像和验收证据中都不出现秘密原文或完整数据库 URL。
8. 发布完成后，证据明确绑定源提交、应用构建标识、部署目标、迁移状态、备份/恢复、smoke
   结果、演示结果和已知限制；没有实际证明的条件不会被写成已经完成。

## Goals

- 为单台个人服务器提供可重复、最小且可运维的生产部署交付，使 app、Web 和 PostgreSQL
  从同一精确版本启动并通过健康检查。
- 在个人域名上提供有效 HTTPS、必要安全头、受控请求边界和不直接暴露数据库的网络边界。
- 提供安全的显式迁移、备份、隔离恢复、部署验证、故障处理、凭据轮换和应用回滚能力。
- 在全部现有质量门禁通过的精确发布候选上，使用 LP-04 合成数据和脚本证明真实域名的核心
  演示故事。
- 形成可复核的发布证据和已知限制，同时严格保留 Engineering Lifecycle 的独立部署/发布
  授权门禁。
- 在同一 LP-05 交付中同步项目管理入口，精确记录 LP-04 关闭事实和 LP-05 当前状态。

## Acceptance criteria

1. 一个精确源提交能够生成不可变、可识别且不依赖开发目录的生产应用构建；构建包含当前
   API 和 Web 资产，启动时可记录非敏感版本标识，且不使用浮动 `latest` 作为验收依据。
2. 生产配置与本地开发配置明确分离；生产数据库只在私有运行网络内可达，公网只暴露 HTTPS
   所需入口。应用和数据库具有可用健康检查、受控重启行为和持久化数据位置。
3. 在符合前置条件的空服务器上，新的运维者仅按版本化文档即可安装并启动发布候选；启动
   顺序保证数据库健康、显式迁移成功、应用 readiness 通过后才把候选视为可服务。
4. 个人域名使用受信任的有效 HTTPS 证书，HTTP 安全重定向到 HTTPS；验收确认 CSP、传输
   与内容类型等必要安全头生效，既有普通请求和报告请求的大小边界没有被代理绕过。
5. 公网 `GET /health/live` 能区分进程存活，`GET /health/ready` 能反映数据库与迁移状态；
   数据库不可达、迁移缺失/漂移或应用未就绪时，部署 smoke 失败且业务路由不被误报为可用。
6. 生产入口保持 LP-01 至 LP-04 已验收的 API、OpenAPI、状态码、幂等、确认 cookie、同源
   Web 路由和 Skill 行为；反向代理不删除请求关联信息、不缓存动态私密响应，也不改变人类
   确认边界。LP-05 不引入破坏性公共契约变更。
7. 生产秘密只通过仓库外受限配置注入；默认示例使用无效占位符。AI token、human-control
   token、cookie、数据库密码/URL、TLS 私钥和备份密钥不进入 Git、镜像层、进程参数、普通
   日志、错误页面、截图、测试快照或验收记录。
8. 运维文档提供 AI 与 human-control 凭据的生成、首次配置和轮换流程；一次隔离验证证明
   轮换后新凭据生效、旧凭据不再授权，并且两类凭据保持不同且不由 AI Skill 接触。
9. 备份流程可对运行数据库创建一致、受访问控制且不进入 Git/Web 根目录的备份；默认运行
   策略为每日一次并保留最近 7 份，执行结果和失败可被运维者发现，但日志不泄露数据正文或
   凭据。
10. 至少一份生产候选备份被恢复到明确隔离的临时数据库；恢复验证证明三份既有迁移校验
    正确、关键合成记录可读、LP-04 核心演示读取可完成，且生产数据库没有被 reset、drop、
    覆盖或连接为恢复目标。
11. 部署流程在迁移前创建可验证备份，显式执行迁移并等待 readiness；迁移、启动或 smoke
    任一步失败时不把新候选标记为成功，也不继续无界重试或留下两个不明确的权威版本。
12. 应用回滚可切回上一已知可用构建并恢复服务；additive migration 默认保留且不自动向下
    回滚。只有已证明数据库与旧应用不兼容、已有可验证预部署备份且获得明确恢复授权时，才
    能执行生产数据库恢复。
13. 精确发布候选通过 `npm run verify`、生产配置校验、容器构建/启动、迁移、部署 smoke、
    备份和隔离恢复 smoke；不得删除、跳过、放宽或只以 mock 代替 LP-01 至 LP-04 的既有
    门禁。
14. 获得单独生产部署授权后，在授权指定的个人域名和服务器上运行部署 smoke；结果至少绑定
    HTTPS URL、源提交、不可变构建标识、部署时间、迁移校验、liveness/readiness 和核心 API/
    Web 读取，不在证据中记录秘密。
15. 真实域名上只使用明确的 LP-04 合成演示数据；按人工演示脚本可以展示 Idea 池、执行项目、
    proposer/executor 切换、进展、待确认问题、支持请求、两种不同结构的动态汇报和完成归档。
16. 从真实部署的受保护备份恢复到隔离环境后，可再次完成核心演示读取；随后真实域名部署
    smoke 仍通过，日志和提交内容的秘密扫描没有发现 token、cookie、数据库 URL、私密正文
    或真实个人数据。
17. 版本化运维文档覆盖：服务器前置、DNS/端口、秘密交付、首次部署、升级、显式迁移、健康
    判断、备份计划、隔离恢复、凭据轮换、日志查看、磁盘/证书/备份故障、应用回滚和已知
    限制。操作者无需阅读实现代码即可执行常规流程。
18. 最小运维可观察性能够让单人发现：应用/数据库未健康、重启循环、证书失败、磁盘空间
    不足、备份失败和部署 smoke 失败；本期不要求企业级监控平台或可用性 SLO。
19. `docs/project-management.md` 和 LP-05 计划在同一交付中更新：LP-04 精确记录上述
    `ACCEPTED_NO_PUBLISH` 关闭事实，LP-05 送验时为 `Ready for Acceptance`；在真实域名
    部署、备份隔离恢复和核心演示均有证据前不得把 LP-05 标为 `Accepted`。
20. 需求确认、RequirementsHandoff、计划批准、代码批准或 merge 均不构成生产部署授权。
    外部部署前必须获得绑定目标服务器/域名和精确候选的独立显式授权；缺少授权或外部输入时，
    LP-05 保持未完成/阻塞并准确记录解除条件。

- 不建设高可用集群、水平扩展、多区域容灾、零停机发布、Kubernetes、服务网格、消息队列、
  自动伸缩或多云编排。
- 不承诺 24×7 SLO、企业级监控、集中日志平台、告警值班、灾备站点、合规认证或渗透测试。
- 不新增或重构 LP-01 至 LP-04 的业务模型、API、Skill、报告协议、Web 功能、登录/权限或
  多租户能力；已验证的部署兼容缺口必须返回 Requirements 显式变更。
- 不把真实公司、客户、个人或商业秘密数据导入公开演示实例。
- 不自动操作未被授权的服务器、SSH、DNS、证书账户、注册商、云平台或备份位置。
- 不建设通用 CI/CD 平台、环境编排产品、秘密管理服务、备份产品或跨项目部署框架。
- 不默认创建 tag、GitHub Release、package、容器注册表发布或外部 Skill 市场发布；这些
  目标若需要，必须分别获得显式发布授权。
- 不删除既有数据库历史、报告 revision、审计、演示证明或 lifecycle 记录来简化部署。

## Failure and recovery expectations

- 外部输入缺失：本地生产构建、文档和隔离恢复证据可以继续；真实部署必须标为 `Blocked`，
  明确列出所缺服务器、域名/DNS、端口、秘密交付、备份位置或发布授权，不推断完成。
- 构建或配置失败：停止候选，不使用开发凭据、浮动镜像或临时手改服务器绕过可复现流程。
- DNS、证书或 HTTPS 失败：不把明文 HTTP 当作发布成功；保留诊断和回退步骤，修复后重新
  执行完整部署 smoke。
- 数据库未就绪或迁移失败：不启动/切换新应用流量；保留原数据和错误证据，先验证备份，再
  由运维者决定修复或回滚。
- 应用 readiness 或核心 smoke 失败：候选不升级为成功版本；回到上一已知构建并重新验证
  liveness、readiness 和核心读取。
- 备份失败：停止会扩大数据风险的发布步骤，保留当前服务，不用空文件或未校验文件冒充
  备份成功。
- 恢复 smoke 失败：只清理明确隔离的临时恢复环境，保留原备份与生产数据；记录失败原因，
  不在生产数据库上反复试验。
- 秘密或私密正文疑似泄露：停止部署/证据发布，轮换受影响凭据，清理可安全清理的派生物并
  记录事件；不得通过删除 Git/lifecycle 历史掩盖问题。
- 演示失败：保留真实失败状态和日志关联，不临时修改数据库或 UI 制造通过；修复必须走正常
  需求、实现和评审边界。

## Public API and compatibility impact

- LP-05 预期不修改领域、数据库 Schema、公共 API、OpenAPI、结构化汇报协议、Skill 语义或
  Web 用户旅程；它部署 `46e021d…` 基线及 LP-05 仅有的运维交付。
- HTTPS 入口必须透传既有方法、路径、状态码、请求 ID、`Authorization`、
  `Idempotency-Key` 和安全 cookie 语义，同时维持同源 Web/API 访问。
- 公开读取、AI bearer 写入和 human-control/scoped-cookie 确认边界保持不变；部署不得把
  Web 角色切换描述为认证或新增隐式权限。
- `/health/live`、`/health/ready` 和 `/openapi.json` 继续作为机器可读运维/契约入口；
  readiness 失败时现有 `/api/v1` 失败语义保持一致。
- 若反向代理、容器或生产环境暴露出必须修改应用契约的真实缺口，Main 必须提供可复现证据
  并返回 Requirements；不得以 LP-05 为由顺带加入未确认的业务或破坏性兼容变更。

## Safety, privacy, permissions, and authorization

- 公开部署只允许明确的合成演示数据。因为 v0.1 没有登录且读取接口公开，任何真实个人数据、
  客户数据、内部 URL、真实证据或商业机密都不得写入该实例。
- 数据库端口、备份目录、管理接口和秘密文件不得公开到互联网或 Web 静态根；只有 HTTPS
  入口对公网开放，内部组件使用最小必要网络和文件权限。
- 生产进程不以 root 身份运行；运行文件系统和持久化写入位置受限，容器/进程能力保持最小。
- 所有镜像、运行时和依赖绑定可审计版本；不以浮动 `latest`、未识别本地构建或未审查外部
  脚本作为生产证据。
- 备份受访问控制，并在宿主或备份介质上加密；加密密钥与数据库凭据分离且不进入仓库。
- SSH、DNS 和服务器操作只针对用户明确授权的目标；先以只读检查解析目标和当前状态，再做
  最小必要变更。未经授权不得修改域名解析、防火墙、运行服务或数据。
- 生产部署、数据库恢复、秘密轮换、tag、Release、package 和外部发布分别属于可产生外部
  状态的动作；只在获得对应的独立显式授权后执行。
- 验收证据使用摘要、状态和脱敏标识，不收集秘密原文、完整数据库 URL、cookie、SSH 私钥、
  DNS 凭据或演示请求正文。

## Release impact

- LP-05 的目标发布对象是一套运行在用户指定单台个人服务器和个人域名上的 v0.1 HTTPS
  服务。Requirements 确认只授权后续设计/实现流程，不授权创建或修改该外部部署。
- 生产部署必须在精确候选通过计划/代码评审、required checks 和本地/隔离发布门禁后，按
  Engineering Lifecycle 的 `explicit-per-release` 策略再次获得绑定目标与候选的授权。
- 若用户没有提供目标、访问方式、DNS 控制、秘密交付、备份位置、公开演示数据许可或明确
  部署授权，可以完成“发布就绪”资产，但不能声称 REQ-026/AC-019 通过，也不能正式接受
  LP-05。
- 默认不创建 tag、GitHub Release、package、容器注册表制品或外部 Skill 发布；若后续需要，
  每一类 release target 都必须单独列明并授权。
- 成功发布证据必须记录实际 URL、精确源提交/构建标识、迁移、备份/恢复、部署 smoke、演示
  结果和已知限制；不得记录秘密。

## Assumptions

- `46e021d261fd8a663c83430a551f5674365ccf14` 是 LP-05 唯一权威代码基线，且 LP-01 至
  LP-04 的契约和正式验收结论保持有效。
- 目标是单台用户控制的 Linux 个人服务器，可运行受支持的容器运行时/Compose，并允许公网
  80/443；不要求多机或云厂商专有能力。
- 用户拥有一个可用于该服务的个人域名及 DNS 修改能力，并会在发布授权时提供准确目标；
  仓库与 Requirements 文档不保存 SSH、DNS 或注册商凭据。
- 该公开实例只承载 LP-04 合成演示数据；默认允许互联网用户读取这些合成数据，但写入和
  高影响确认仍受既有 token/capability 边界保护。
- 用户会通过仓库外安全通道提供 AI、human-control、数据库和备份加密所需秘密；Main 不
  生成或持有用户的长期 SSH/DNS 凭据。
- v0.1 接受单实例维护窗口，不要求零停机；恢复目标以“完成一次可复现隔离恢复并通过演示
  读取”为准，不定义企业级 RPO/RTO。
- 默认备份策略为每日一次、保留最近 7 份；确切目录、容量、加密方式和责任人在发布前确认。
- 原计划的 2026-08-06 演示目标仍是排期意图，但验收必须以真实门禁证据为准，不能为赶日期
  跳过评审、备份恢复或独立发布授权。
