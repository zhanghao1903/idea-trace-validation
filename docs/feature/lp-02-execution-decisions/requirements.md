## Problem

LP-01 已经建立可运行的 Idea 创建、澄清、显式推进和基础项目读取能力，但推进后的
项目只能停留在 `PLANNING / QUEUED`。执行者还不能在权威系统中开始、暂停或恢复
项目，也不能提交进展、阻塞、待确认问题、支持请求、证据和验证结论。想法提出者也
没有可追踪的回应和高影响确认入口。

因此，当前链路只能证明“Idea 可以成为项目”，不能证明“项目可以被执行、治理并形成
可纠正的结论”。LP-02 需要在不引入完整网页、用户系统或复杂审批流的前提下，建立
项目执行与决策闭环，并继续复用 LP-01 已验收的权威数据、幂等、版本、事务、审计和
错误语义。

## Desired scenarios

1. 执行者从现有 `QUEUED` 项目开始执行；系统显式改变状态，并保留原因、操作者、
   版本和时间历史。
2. 执行者暂停项目并填写原因，随后用恢复说明和下一步恢复；非法或过期转换被拒绝，
   当前事实不变。
3. 执行者提交包含摘要、完成工作、当前阶段、下一步和证据的一次进展；进展被追加
   保存，但不会隐式改变项目生命周期状态。
4. 执行者分别创建阻塞、待确认问题和支持请求；想法提出者回应或解决后，双方仍能
   读取原始背景、影响、回应和完整状态历史。
5. 执行者记录链接、产物标识、指标或说明类 Evidence，并在同一项目的进展或结论中
   引用；系统不抓取外链、不上传文件，也不接受跨项目引用。
6. 执行者提交带证据摘要、限制、不确定性和建议去向的版本化验证结论；修改内容产生
   新版本，不覆盖旧结论。
7. 人在专用确认入口看到与具体结论、操作和项目版本绑定的摘要，批准或拒绝；普通
   进展、关注事项和非终态转换不逐条等待批准。
8. 完成、停止、移交或重开项目只在有效人类确认后生效；过期、已使用、载荷变化或
   版本变化的确认不能产生部分写入。
9. 已完成项目填写原因并确认重开后回到执行中；原完成时间、结论、确认和重开原因
   继续可追踪。
10. 网络未知结果、并发写入或错误内容都能通过幂等重试、版本冲突提示和追加式纠正
    恢复，不静默删除或改写历史。
11. LP-02 准备正式验收时，唯一项目管理入口准确记录 LP-01 已验收的关闭证据和
    LP-02 的实际状态，不把“已合并”“已验收”和“已发布”混为一谈。

## Goals

- 让现有等待执行项目进入可解释、可恢复的执行生命周期。
- 让进展、阻塞、待确认问题、支持请求、回应和 Evidence 成为权威、可读取的记录。
- 形成包含证据、限制、不确定性和建议去向的版本化验证结论。
- 仅对结论以及完成、停止、移交和重开等高影响操作要求专用人类确认。
- 保证确认与确切载荷、结论版本和项目版本绑定，且有过期和单次使用保护。
- 保留进展、事项、结论、确认、纠正和生命周期变化的追加式历史。
- 延续 LP-01 的幂等、乐观并发、原子审计、统一错误、访问边界和可重复验证能力。
- 更新项目管理事实，使 LP-01 的正式验收与 LP-02 的交付状态可追踪。
- 为 LP-03 的结构化汇报和双角色体验提供稳定执行数据，不提前实现 LP-03。

## Functional requirements

| ID | Requirement |
| --- | --- |
| LP2-REQ-001 | LP-02 必须从 LP-01 权威合并基线演进；既有 Idea、澄清、项目、假设、幂等记录和审计历史必须在升级后保持可读，现有 `PLANNING / QUEUED` 项目无需重建即可进入 LP-02 流程。 |
| LP2-REQ-002 | 项目生命周期必须支持显式开始、暂停和恢复。开始要求存在明确下一步；暂停要求非空原因；恢复要求非空恢复说明和下一步。非法前置状态不得被接受。 |
| LP2-REQ-003 | 项目阶段与生命周期状态必须分别表达。只有显式生命周期或阶段操作可以改变权威状态；提交进展、事项、证据、结论或展示数据都不得隐式改变状态。 |
| LP2-REQ-004 | 每次进展必须追加保存稳定 ID、顺序、摘要、已完成工作、下一步、提交时项目状态和阶段、Evidence 引用、事实发生时间、服务端提交时间及声明操作者。 |
| LP2-REQ-005 | 已保存进展不得原地覆盖或物理删除；需要更正时必须追加可追踪纠正并指向被更正记录，同时让读取方区分当前解释与原始事实。 |
| LP2-REQ-006 | 系统必须支持 `BLOCKER`、`DECISION_REQUEST` 和 `SUPPORT_REQUEST` 三类关注事项，并分别保存其背景、影响以及解除说明、选项或建议与决策影响、所需支持与期望响应方等必要内容。 |
| LP2-REQ-007 | 关注事项必须至少支持 `OPEN`、`NEEDS_INFO`、`RESOLVED` 和 `CLOSED` 的可解释处理状态；回应、补充、解决或关闭必须追加记录，不能删除原始描述和既有回应。 |
| LP2-REQ-008 | Evidence 必须是同一项目内可引用的元数据，至少区分链接、受控产物标识、指标和说明，并保存标题、摘要、事实发生时间和声明记录者。系统不得抓取外链、执行内容或承担通用文件上传。 |
| LP2-REQ-009 | Evidence 外链只允许受支持的安全 HTTPS 定位方式；不存在、无效、非 HTTPS 或跨项目 Evidence 引用必须被拒绝，且不得留下部分业务写入。 |
| LP2-REQ-010 | 验证结论必须形成不可变版本，至少包含 Evidence 摘要和引用、已知限制、不确定性、建议去向及补充说明；建议去向固定为继续、调整、停止或移交。 |
| LP2-REQ-011 | 新结论版本不得覆盖旧版本。读取结果必须清楚区分草稿、待确认、已确认和已被后续版本取代的结论，并保留版本间关系。 |
| LP2-REQ-012 | 最终验证结论以及完成、停止、移交、重开项目必须经过专用人类确认；普通进展、关注事项、Evidence、开始、暂停和恢复不要求逐条确认。 |
| LP2-REQ-013 | 人类确认必须绑定一个不可变操作摘要，摘要至少覆盖目标项目、操作、结论版本或相关载荷以及预期项目版本；绑定内容发生变化后，原确认不得继续使用。 |
| LP2-REQ-014 | 每次确认机会必须具有服务端可观察的有限有效期并只能成功消费一次。批准、拒绝、过期、重复使用和摘要不匹配都必须产生确定结果。 |
| LP2-REQ-015 | 人类确认必须通过与普通 AI bearer 写入分离的控制能力完成；仅持有 AI 写入凭据不能自行批准高影响操作。本阶段仍不声称认证了具体自然人身份。 |
| LP2-REQ-016 | 确认原始秘密不得以明文持久化、写入日志、错误、URL 查询参数或响应正文。系统只能保存完成校验和追踪所需的安全表示及脱敏元数据。 |
| LP2-REQ-017 | 人类可以批准或拒绝待确认操作。拒绝必须保留结论或请求及拒绝记录，但不得改变项目终态；批准必须把确认记录、结论状态、项目变化和审计事件原子保存。 |
| LP2-REQ-018 | 完成项目必须引用已确认结论；停止必须对应“停止”建议；移交必须对应“移交”建议。任何终态操作都必须保留完成摘要、服务端时间和对应确认。 |
| LP2-REQ-019 | 已完成项目只能在提供非空原因并通过有效人类确认后重开；重开后项目回到执行中，原结论、完成记录、确认和历史不得丢失或被改写。 |
| LP2-REQ-020 | 对进展、关注事项、Evidence、结论和状态变化的纠正或撤销必须以追加式补偿记录表达，并引用原记录；不得提供静默物理删除业务历史的成功路径。 |
| LP2-REQ-021 | 所有 LP-02 写请求必须延续 LP-01 的幂等语义：相同键与相同意图重放原确定结果，不新增记录；相同键表达不同意图时返回明确冲突并保留首次结果。 |
| LP2-REQ-022 | 所有修改既有项目的 LP-02 操作必须检查预期项目版本。过期版本不得覆盖新事实，并必须返回当前版本或明确的重新读取提示。 |
| LP2-REQ-023 | 每个成功 LP-02 命令必须在同一事务中保存业务事实、递增权威项目版本并追加脱敏审计事件；任一步失败时都不得报告成功或留下部分写入。 |
| LP2-REQ-024 | 项目列表和详情读取必须继续从同一权威数据产生 proposer 与 executor 投影，并能读取当前生命周期、最新进展、未处理关注事项、Evidence、结论和有稳定顺序的历史；投影不得形成平行状态。 |
| LP2-REQ-025 | LP-02 API 必须延续 LP-01 的版本化路径、稳定 ID、服务端时间、请求关联、统一成功/错误信封和 readiness gate，并提供机器可读的新增及扩展契约。 |
| LP2-REQ-026 | LP-01 已验收的 Idea 创建、澄清、推进和读取行为必须保持兼容；既有路由和字段不得被静默移除或改义，扩展的项目状态、阶段和对象必须在契约及迁移说明中明确。 |
| LP2-REQ-027 | LP-02 必须具有自动化领域、契约、持久化、API 和客观闭环测试，覆盖成功路径、非法转换、幂等重放/冲突、版本冲突、确认过期/重放/载荷变化、跨项目引用和事务回滚。 |
| LP2-REQ-028 | LP-02 准备正式验收前，`docs/project-management.md`、LP-01 计划和 LP-02 计划必须在同一交付变更中同步实际证据：LP-01 为 `Accepted`，记录 `ACCEPTED_NO_PUBLISH`、merge/acceptance/closure 标识和无发布产物事实；LP-02 为 `Ready for Acceptance` 并指向其客观验证证据，但不得提前写成 `Accepted` 或已发布。 |

## Acceptance criteria

| ID | Requirement IDs | Observable criterion |
| --- | --- | --- |
| LP2-AC-001 | LP2-REQ-001、LP2-REQ-026 | Given 一个含 LP-01 Idea、假设和 `PLANNING / QUEUED` 项目的数据库，when 应用 LP-02 升级并读取原 API，then 原对象、ID、版本和历史保持可读，且该项目可直接开始 LP-02 执行。 |
| LP2-AC-002 | LP2-REQ-002–003、LP2-REQ-022–023 | Given 一个排队项目，when 开始、暂停并恢复，then 每步只接受合法前置状态，要求的原因/下一步存在，项目版本逐步增长且历史完整；用旧版本重放转换返回冲突。 |
| LP2-AC-003 | LP2-REQ-004–005、LP2-REQ-021–023 | Given 一个执行中项目，when 提交含完成工作、下一步和 Evidence 的进展，then 新进展可读取且项目状态不变；相同幂等请求不重复，不同载荷冲突。 |
| LP2-AC-004 | LP2-REQ-008–009 | Given 同项目 HTTPS 链接、指标和说明类 Evidence，when 创建并引用，then 元数据可读取且系统不抓取内容；非 HTTPS、未知或跨项目引用被拒绝且无部分写入。 |
| LP2-AC-005 | LP2-REQ-006–007、LP2-REQ-020、LP2-REQ-024 | Given 阻塞、待确认问题和支持请求各一项，when 分别补充、回应、解决或关闭，then proposer/executor 读取相同当前状态，并能看到原背景、影响、全部回应和状态历史。 |
| LP2-AC-006 | LP2-REQ-010–011 | Given 已产生 Evidence，when 提交包含限制、不确定性和建议去向的结论并修订，then 两个不可变版本均可读取，当前版本关系明确，且提交本身不隐式完成项目。 |
| LP2-AC-007 | LP2-REQ-012–017 | Given 一个待确认结论或高影响操作，when 人通过专用控制能力批准，then 确切摘要被消费一次并原子生效；仅使用 AI 写入凭据、拒绝或重复消费都不能使高影响操作生效。 |
| LP2-AC-008 | LP2-REQ-013–017、LP2-REQ-022–023 | Given 确认已过期、项目版本变化、结论被修订或操作载荷变化，when 尝试批准，then 返回确定失败，项目、结论和确认消费状态不出现部分或矛盾写入。 |
| LP2-AC-009 | LP2-REQ-010–019 | Given 分别具有有效建议的项目，when 经人确认完成、停止或移交，then 项目进入已完成状态并引用正确结论和确认；建议不匹配时操作被拒绝。 |

| LP2-AC-011 | LP2-REQ-005、LP2-REQ-007、LP2-REQ-011、LP2-REQ-020 | Given 已保存的进展、事项回应或结论存在错误，when 追加纠正或新版本，then当前投影反映新解释，原记录仍存在且可从关系链追溯。 |
| LP2-AC-012 | LP2-REQ-021–023、LP2-REQ-027 | Given 任一 LP-02 写入在业务事实、版本、确认或审计保存期间模拟失败，when 事务结束并以同一幂等键安全重试，then 失败尝试没有部分记录，恢复后只产生一份成功结果。 |
| LP2-AC-013 | LP2-REQ-024–026 | Given 项目具有多条进展、关注事项、Evidence 和结论，when 分别读取 proposer 与 executor 投影和机器可读契约，then 两者引用相同权威 ID、状态和版本，新增字段及错误语义均有契约定义。 |
| LP2-AC-014 | LP2-REQ-015–016、LP2-REQ-025 | Given 无效访问能力、确认秘密或包含敏感内容的请求，when 调用 LP-02 API 并检查日志/错误/历史，then 访问按边界拒绝且秘密、cookie、数据库连接信息和完整敏感正文均未泄露。 |
| LP2-AC-015 | LP2-REQ-028 | Given LP-02 准备正式验收，when 查看唯一管理入口及 LP-01/LP-02 计划，then LP-01 显示 `Accepted` 和精确关闭证据、无发布产物，LP-02 显示 `Ready for Acceptance` 和验证证据，LP-03 仍未被自动验收或授权。 |
| LP2-AC-016 | LP2-REQ-001–028 | Given 一个由 LP-01 推进产生的排队项目，when 客观场景依次开始执行、提交进展和三类关注事项、回应并解决事项、记录 Evidence、提交带限制的结论、确认完成、再填写原因确认重开，then 只存在一条一致项目主线，所有状态、版本、结论、确认、错误和原始历史符合本快照。 |

- 不实现 MCP Server、通用文件上传、对象存储、外链抓取或远程内容可信校验。
- 不让 AI 生成的文本、结构化汇报或普通 AI 写入凭据绕过人类确认。
- 不自动执行“移交产品线”的外部流程；本期只保存被确认的建议和项目结果。
- 不在 Requirements 中决定表结构、路由命名、token 格式、加密算法、包版本或部署拓扑。
- 不建立自研 Engineering Lifecycle 授权引擎、GitHub pagination、plugin provenance、
  完整 lifecycle simulator、通用 future-state validator 或大规模 mutation/negative
  harness。
- 不复用 LP-01 或 lightweight planning feature 的实现授权；LP-02 必须独立确认、
  计划、评审、实现和验收。

## Failure and recovery expectations

- 输入不完整、状态非法、建议不匹配或引用无效时，系统保持当前项目事实并返回稳定
  错误码、可理解说明、是否可重试及适用的恢复提示。
- 响应未知时，调用方使用相同幂等键和相同意图重试；系统返回首次确定结果，不要求
  调用方猜测是否成功。
- 相同幂等键表达不同意图时，保留首次结果并拒绝新载荷；新业务意图使用新键。
- 版本冲突时不自动覆盖；调用方重新读取项目、合并意图后基于新版本重试。
- 进展、事项、Evidence 或结论内容错误时使用追加式纠正、新回应或新版本；不删除
  原记录。
- 确认被拒绝、过期、已使用、载荷变化或版本变化时，高影响操作不生效；需要时基于
  当前事实发起新的确认。
- 数据库、事务、审计或确认消费失败时不得报告成功；恢复后能够安全重试。
- readiness 不满足时业务 API 不接受写入；恢复后已提交数据仍可读取。

## Public API and compatibility impact

LP-02 将扩展现有 `/api/v1` 项目能力，增加执行转换、进展、关注事项、Evidence、
结论、确认和历史读取所需的版本化 API。具体路由拆分由 Main 的技术计划决定，但
每项需求都必须在机器可读契约中可操作、可观察。

LP-01 已验收的 Idea 和项目读取客户端必须继续工作。现有 ID、请求关联、幂等键、
`expectedVersion`、成功/错误信封和 readiness 语义继续复用；项目状态、阶段或响应
字段的扩展必须显式记录，不能静默重写已验收的 LP-01 契约产物。破坏性变化需要单独
兼容说明和迁移路径。

## Safety, privacy, permissions, and authorization

- v0.1 仍是无用户系统的单工作空间演示；actor 和 role 只表示声明归属，不代表已
  认证自然人身份。
- AI 执行写入继续要求部署级 bearer 凭据；人类确认使用独立、最小权限、一次性的
  控制能力。任何单一 AI 写入能力都不能完成自我批准。
- 确认秘密只在必要边界传递，持久化时不得保存可直接使用的明文；日志、错误、审计
  和 URL 不得泄露秘密。
- 公开读取边界沿用 LP-01，因此演示环境只能使用虚构、非敏感数据，不得录入真实
  商业机密、个人数据、访问 token 或凭据。
- Evidence 是不受系统背书的元数据。系统不得主动抓取或执行链接内容，界面和 API
  不得把外链存在等同于证据已被验证。
- 客户端不能伪造服务端 ID、权威版本、提交时间、确认时间或审计结果。
- 输入必须有结构、数量和大小边界；错误和审计只保留诊断所需的脱敏摘要。
- 本快照不授权生产凭据配置、外部数据导入、部署、发布、tag 或 Release。
